# Home Credit Risk Scoring

Building a credit risk scoring pipeline on the Kaggle **Home Credit Default Risk** dataset: gradient-boosted trees with feature engineering, tuning, calibration, and explanation.

The task is binary classification on seven relational tables. For each applicant in `application_train`, predict `P(TARGET = 1 | x)`, then calibrate the probability and explain the drivers. Positives are roughly 8% of the data.

> **Project status: Phases 0-3 done, E1 baseline logged, Phase 4 (E2 ablation) in progress.** Person A's dataset is frozen (`data/processed/datasets/`, contract `datasets_v1`, 180 predictors), the split protocol is single and fixed, `src/cv` + `src/models` + `src/evaluation/metrics.py` are implemented, and `tests/` passes (28 tests). The notebooks 01..04 build the data; `src/` only models it. `AGENTS.md` defines the workflow, phases and ownership; `INIT.md` holds the research questions, dataset specification and methodology.

## Scope

- **Models:** LightGBM, XGBoost, CatBoost, plus a weighted-average / stacked ensemble. A logistic-regression sanity baseline is optional. Deep learning is out of scope unless explicitly approved.
- **Primary metric:** ROC-AUC. Also reported: Gini (`2*AUC - 1`), KS, PR-AUC, Brier score, ECE, and recall/precision at fixed thresholds.
- **Research questions:**
  - **RQ1** — How much do features from the auxiliary tables add over the main application table alone?
  - **RQ2** — After tuning, how do the three GBDTs and their ensemble differ in AUC, KS, and calibration?
  - **RQ3** — Which imbalance-handling technique and tuning strategy works best per model?
  - **RQ4** — Do the models agree on the most important features (SHAP / gain; top-k Jaccard, Spearman)?

```bash
git clone git@github.com:ngTanPhuc/home-credit-risk.git
cd home-credit-risk
uv sync
```

`uv sync` creates `.venv/` from `.python-version` and installs the locked dependencies from `pyproject.toml` / `uv.lock`. Commit `uv.lock`; never hand-edit it.

Verify the environment:


### 4. MLflow tracking

Runs log to `./mlruns` (`mlflow.tracking_uri` in `configs/base.yaml`), laid out as `mlruns/<experiment_id>/<run_id>/` with `meta.yaml`, `params/`, `metrics/`, `tags/` and `artifacts/`. Each run's artifacts are `config.json`, the fold/summary/importance CSVs, the OOF Parquet and the run JSON. `mlruns/` is gitignored; a plain-JSON copy of every run also lands in `reports/runs/`.

View the UI:

```bash
MLFLOW_ALLOW_FILE_STORE=true uv run mlflow ui --backend-store-uri ./mlruns --port 5000
```

Then open <http://127.0.0.1:5000>. MLflow 3.x refuses the filesystem backend unless `MLFLOW_ALLOW_FILE_STORE=true` is set; the runner sets it internally, the CLI does not.

Delete a run and its artifacts (irreversible):

```bash
MLFLOW_ALLOW_FILE_STORE=true uv run python -c "
import mlflow
from mlflow.tracking import MlflowClient
mlflow.set_tracking_uri('mlruns')
MlflowClient().delete_run('<run_id>')   # soft delete -> mlruns/.trash/
"
rm -rf mlruns/.trash/*                  # frees the disk
```

On this local store `rm -rf mlruns/<experiment_id>/<run_id>` does the same in one step. Deleting a run does not touch `reports/`, which the runner writes independently.

On Kaggle, export `mlruns/` as notebook output, or read the JSON fallback under `reports/runs/`.

## Pipeline

Person A's notebooks build the data and are standalone (no `src/` imports). They locate the repo root via `HOME_CREDIT_ROOT` or by walking up to `data/raw/`, so run them from the repo root. They abort when a manifest or hash does not match. Jupyter is not a project dependency; use Kaggle or a local Jupyter / VS Code session.

| Notebook | Reads | Writes |
|---|---|---|
| `01_data_overview_eda` | `data/raw/*.csv` | `data/interim/*.parquet`, `data/splits/` |
| `02_data_cleaning` | `data/interim/` | `data/processed/*.parquet`, `cleaning_manifest.json` |
| `03_feature_engineering` | `data/processed/*.parquet` | `data/processed/features/*.parquet`, `feature_manifest.json`, `feature_catalog.csv` |
| `04_dataset_assembly_validation` | features + split | `data/processed/datasets/{train,val,test}.parquet`, `dataset_manifest.json`, `feature_contract.json` |

Person B's modelling code reads only the frozen dataset and validates it against the contract. All scripts take a YAML config and expose `--sample N` (quick checks) and `--force` (recompute).

```bash
# Run an experiment (E1 baseline, E2 ablation, ...)
uv run python -m src.cv.runner --config configs/experiments/E1_baseline.yaml

# Quick smoke run: 500 development rows across the 5 folds, hold-out untouched
uv run python -m src.cv.runner --config configs/experiments/E1_baseline.yaml --sample 500

# Tune (resumable via Optuna SQLite storage)
uv run python -m src.tuning.optuna_search --config configs/experiments/E4_tuning.yaml

# Final hold-out evaluation — run ONCE, deliberately
uv run python -m src.evaluation.holdout --config configs/experiments/E5_models.yaml --confirm-final

# Explanation
uv run python -m src.explain.shap_analysis --config configs/experiments/E7_explain.yaml
uv run python -m src.explain.agreement --config configs/experiments/E7_explain.yaml
```

Only the `src.cv.runner` commands work today; the others land with their phases.

## Splits and evaluation protocol

- One fixed split, created once by `notebooks/01_data_overview_eda.ipynb`: 80% development, 20% stratified hold-out (hold-out seed `2026`).
- The development set uses 5-fold stratified CV (seed `42`); fold ids live in the `fold` column of `data/processed/datasets/train.parquet`, validated against `data/splits/train_val_metadata.json`.
- **Never re-split or regenerate the split** once it exists. Every model and experiment uses the same folds.
- The hold-out is read exactly once, by `src/evaluation/holdout.py --confirm-final`. No tuning or model selection may touch it; `src/cv/dataset.py` raises `PermissionError` on any other attempt to load `val.parquet`.
- The split is random by design: the data has no application date, so a temporal split is impossible. This is a documented limitation.
- Final experiments repeat with 3 model seeds (the split stays fixed) and report mean ± std.

## Kaggle workflow

Kaggle sessions are time- and memory-limited (16 GB RAM ceiling):

1. Push code to GitHub, then clone/pull it in the notebook, or attach the repo as a Kaggle dataset.
2. Raw data is mounted read-only under `/kaggle/input/home-credit-default-risk/`.
3. Write processed Parquet and `mlruns/` to `/kaggle/working/`, then re-attach them as a Kaggle dataset so later sessions skip recomputation.
4. Keep any Kaggle launcher notebook thin: install/sync deps, set paths, call `python -m src.<module> --config ...`. No pipeline logic in notebooks.
5. Heavy steps are resumable: skip existing outputs unless `--force`; use Optuna SQLite storage for tuning.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `uv: command not found` | `uv` is installed at `~/.local/bin/uv`; add it to `PATH` (`source $HOME/.local/bin/env`) or call the absolute path. |
| MLflow exits with `The filesystem tracking backend ... is in maintenance mode` | Prefix the command with `MLFLOW_ALLOW_FILE_STORE=true`; MLflow 3.x requires the opt-in for `./mlruns`. |
| `FileNotFoundError: Dataset split not found` | Build the dataset with notebooks 01..04, or copy `data/processed/datasets/` and `data/splits/` from a machine that has it. |
| `ValueError: train.parquet has ... rows but the split declares ...` | The dataset and the split metadata come from different runs. Rebuild from notebook 01 instead of mixing files. |
| A package has no wheel for Python 3.14 | Lower `.python-version` (e.g. to `3.13`), then `uv lock` and `uv sync`. Check which interpreter the Kaggle image provides before matching it. |
| Kaggle download returns 403 | Accept the competition rules on the Kaggle website first. |
| Kaggle CLI complains about credentials | `chmod 600 ~/.kaggle/kaggle.json`; the file must be valid JSON. |
| Out-of-memory on `bureau_balance` / `installments_payments` | Use chunked reads, `usecols`, downcasting, and per-group aggregation; never load with default dtypes. |
| Hold-out script refuses to run | It requires `--confirm-final`. That is intentional; use CV for all development. |
